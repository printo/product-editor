Scope & mockup notes

  • This mockup is just the calendar primitive. Photo frames, branding, and other artwork that sit alongside the calendar are owned by the surrounding layout (e.g. desk-calendar layout, full-page-calendar layout). The same primitive embeds into all of them via the layout JSON's calendar.{x, y, width, height}.
  • Date number is always visible (top-right of each cell) unless the cell has an imageOverride.
  • Holiday pills auto-load from storage/holidays/en-IN/<year>.json (seeded from Nager.Date). User can't delete them — only override the whole cell with an image.
  • User event pills stack with holidays (user-first precedence). Hard cap = 3 entries per cell total; anything beyond the cap is silently suppressed (no +N more badge — PRD §11.10).
  • Cell text auto-fits to the cell width (the real renderer uses a binary-search font-size helper; this mockup uses CSS text-overflow: ellipsis for simplicity).
  • Themes map to storage/calendar_styles/{modern-minimalist,modern-genz,weekday-highlight}.json. Ops picks at layout creation; customer can't switch.
  • Weekday-highlight theme: Sunday cells get a light-red fill + 1.5 px red outline + red date number (the "auto-fill light shade for cells bg AND dark shade for border" treatment). Saturday cells get a soft-blue tint.
  • Default week-start: Sunday (en-IN convention). Toggleable per layout.
  • Calendar type — English vs Financial. english runs Jan→Dec; financial runs Apr→Mar (India's fiscal year). In financial mode the Year selector reformats to FY 2026–27 and the Month dropdown reorders so April is first. Under the hood the grid math, holidays, and 300 DPI renderer stay Gregorian — only the navigation UI changes. Picking March from FY 2026–27 resolves to March 2027 (the FY's final month). PRD §4.2.1 gains a calendar.calendarType field; defaults to english for back-compat.
  • Product type — productType: 'calendar' (PRD §10). A 12-month calendar product is a Multi-Surface Product with a top-level productType: 'calendar' tag and a monthRange: { count, defaultYear } field. Ops designs ONE representative month (calendar primitive in one area, photo frames in another); the system materializes 12 surfaces from that single template at editor-mount time. defaultYear: "current" auto-rolls — same layout JSON prints 2026 in 2026 and 2027 in 2027 with zero ops intervention. Same pattern extends to photobook (productType: 'photobook', pageRange: { count, layout }) and any future N-surface bloc product.
  • Per-surface overrides (PRD §10.2.1). The 12 auto-generated surfaces are the starting point, not a permanent constraint. Ops can drill into any individual month (e.g. December for Christmas overlays, February for a hearts decoration) and override its structure — frames, calendar primitive position, decorative overlays. Overrides live in a sparse surfaceOverrides field on the layout JSON, keyed by month surface key; untouched months continue to inherit from the template. A "Reset to template" action returns a customized month to the template's design. Per-surface overrides are field-level replace (not deep-merge) so the contract stays trivial: if ops touched frames on a month, that month uses the overridden array entirely. Customer-controllable fields (themePreset, calendarType) and physical fields (canvas.{widthMm,heightMm,dpi}) cannot be overridden per surface — they stay layout-global to avoid merge ambiguity.
  • Edge-case decisions (PRD §11).
    • One or many calendar primitives per layout (§11.1). Schema is calendars: [] (plural). v1 supports two modes: multi-surface (12 pages × 1 calendar/page — desk calendar) or multi-calendar single-page (1 page × 12 calendars — year-on-one-poster). Constraint: monthRange.count × calendars.length === 12.
    • MAX_ENTRIES precedence: user-first (§11.14). Hard cap of 3 total entries per cell. User entries fill slots first; holidays fill any remaining slots; no overflow badge (§11.10 — anything beyond the cap is silently suppressed). This mockup now follows this rule.
    • Out-of-month cells: date number only (§11.12). Filler cells from prev/next month show greyed date, no pills, no overrides.
    • Font: single bundled default — Inter Variable (§11.7). No font picker exposed to ops or customer. Eliminates render-time font drift.
    • Calendar type flip mid-edit (§11.4): warning modal if orphaning entries. Multi-surface partial render failure (§11.5): fail-all-or-nothing with retry warning. ZIP filenames (§11.6): from Multi-Surface displayLabel (e.g. January 2026.png).
    • Per-month theme override: NOT supported in v1 (§11.2). Workaround: per-month decorative overlays.
    • Layout versioning (§11.16): none — embed always loads the current layout JSON. Last-write-wins.
  • Ops vs Customer controls in production. The 4 controls visible in this mockup are not all customer-facing. In production:
    • Customer-controllable on the preview page: Theme preset (Minimalist / Gen-Z / Weekday-Highlight), Gen-Z palette (when theme=Gen-Z), Calendar type (English / Financial), per-cell entries + image overrides.
    • Ops-locked at layout creation: Aspect ratio (physical SKU), Week starts (locale convention).
    • Auto-populated: Year (English ⇒ current calendar year; Financial ⇒ current FY-start year, i.e. today.month ≥ April ? currentYear : currentYear − 1). No customer year picker.
    All 4 controls remain interactive in this mockup for prototyping convenience — the customer/ops split lives in the surrounding component code (CalendarLayoutEditor.tsx for ops, CalendarProductPreview.tsx for customer).
  • Image override replaces the entire cell content. Reuses the existing chunked-upload + MediaPipe auto-orientation pipeline.
  • The 300 DPI server-rendered output will look identical to this preview (paritied via PRD §4.3 "identical math").
